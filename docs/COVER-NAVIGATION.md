# Cover navigation performance — October 9, 2026

The previous CoverImage always initialized managed-cover resolution to null on mount. Switching pages unmounted the old page, so even a cached IPC result displayed “Loading cover” until another effect resolved it. All resulting img elements were lazy, and the resolution cache did not represent browser decode readiness. Returning to All Books also constructed an equivalent query and unnecessarily refreshed the catalog.

Every cover surface now shares a decode queue and a synchronous ready lookup. A preloaded cover renders an eager img on its first remounted render. Cold offscreen covers wait for IntersectionObserver proximity (300 CSS pixels); the inspector loads immediately. Environments without IntersectionObserver load through the same queue. External/sample covers also use browser decoding. Existing themes, logo, Windows chrome, storage commands and database behavior are preserved.

The app warms the first 24 filtered books, up to eight Reading and four Want to Read covers, and the first three covers from each of the first four collections. References are deduplicated and capped at 48 per preload request; at most 48 speculative jobs wait in the queue. Four resolution/decode operations run concurrently, with visible requests promoted ahead of speculative jobs. At most 64 decoded Image objects are retained with least-recently-used eviction. Native reference resolution remains separately bounded to 128 entries, now with least-recently-used ordering. These are count limits, not a guaranteed byte-memory ceiling, especially for large external images.

Failed reads and decodes can be retried after remount. Stalled image loads time out after 15 seconds and release their slot. Changed cover references use a new key. Successful ZIP/JSON restores and demo reset invalidate resolution and readiness together, notify mounted covers, cancel queued jobs, and prevent older completions from repopulating readiness. A failed restore preserves cached covers. An older failed IPC read cannot remove a newer replacement entry.

Returning to the same Library scope keeps the existing query object, avoiding another loading skeleton/catalog refresh. Actual status/collection/filter changes still fetch through the existing service contract. Broader catalog-query optimization is outside this change.
